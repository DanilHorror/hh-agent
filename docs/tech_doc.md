# Технический документ: агент автоматизации поиска работы на hh.ru

**Версия:** 0.1 (черновик)
**Статус:** до реализации, без кода

---

## 1. Цель и границы проекта

Автоматизировать две задачи соискателя на hh.ru:

1. **Мониторинг** — обнаружение новых вакансий по заданным фильтрам как можно раньше после публикации.
2. **Отклик** — формирование персонализированного отклика и отправка его от имени пользователя.

**Явно вне рамок:** массовая рассылка одинаковых откликов, обход капчи/антибот-защиты специальными средствами, работа без ведома и подтверждения пользователя на этапе принятия решений.

Ключевой принцип архитектуры — **система усиливает пользователя, а не заменяет его без контроля**. Это одновременно снижает риск блокировки аккаунта и повышает качество откликов.

---

## 2. Ограничения площадки (актуально на сентябрь 2026)

| Ограничение | Детали |
|---|---|
| Публичный API поиска вакансий | С апреля 2026 закрыт для неавторизованных запросов (403 Forbidden); доступ преимущественно у работодателей с модерацией приложения |
| Лимит откликов | Историческое ограничение ~5 бесплатных откликов в день без платного пакета отклика |
| Пользовательское соглашение | Запрещает автоматизированную/массовую рассылку откликов без разбора — риск блокировки аккаунта |
| Антибот-детект | Анализ паттернов запросов, скорости действий, User-Agent, поведения мыши/скролла |

**Вывод:** т.к. официальный API для соискателя частично закрыт, основной канал получения данных — **браузерная автоматизация под залогиненной сессией пользователя**, имитирующая обычный сёрфинг. Это смещает акцент документа на разделы 5 и 6 (человеческий паттерн поведения).

## 3. Высокоуровневая архитектура

```
┌─────────────────┐     ┌──────────────────┐     ┌───────────────────┐
│  Scheduler /     │────▶│  Browser Worker    │────▶│  Data Store        │
│  Orchestrator    │     │  (Playwright)      │     │  (вакансии, статусы)│
└─────────────────┘     └──────────────────┘     └───────────────────┘
                                  │                          │
                                  ▼                          ▼
                         ┌──────────────────┐     ┌───────────────────┐
                         │  LLM Layer        │     │  Notifier          │
                         │  (Qwen локально)  │     │  (Telegram/почта)  │
                         └──────────────────┘     └───────────────────┘
                                  │
                                  ▼
                         ┌──────────────────┐
                         │  Human-in-the-loop│
                         │  подтверждение     │
                         └──────────────────┘
```

### Компоненты

**Scheduler / Orchestrator**
Управляет расписанием запусков, распределяет задачи между воркерами, следит за общими лимитами (сколько действий выполнено за сутки/час).

**Browser Worker**
Единственная точка взаимодействия с hh.ru. Логинится под сохранённой сессией, выполняет поиск, читает карточки вакансий, кликает "откликнуться". Работает через Playwright с постоянным профилем браузера (cookies, localStorage, fingerprint не пересоздаются каждый раз).

**LLM Layer (Qwen)**
Принимает на вход текст вакансии + резюме пользователя. Отдаёт: (а) оценку релевантности, (б) черновик сопроводительного письма. Не имеет прямого доступа к браузеру — работает только с текстом.

**Data Store**
Хранит все увиденные вакансии, их статус (новая / просмотрена / предложена / отправлена / отклонена пользователем / отказ работодателя), метки времени. Нужен, чтобы не откликаться дважды и вести историю.

**Notifier**
Присылает пользователю уведомления о новых релевантных вакансиях и черновики откликов на подтверждение.

**Human-in-the-loop**
Обязательный шаг подтверждения перед отправкой отклика (кнопка "отправить / пропустить / отредактировать").

## 4. Поток данных (data flow)

1. Scheduler запускает цикл проверки (не по жёсткому крону, см. раздел 6.1).
2. Browser Worker открывает страницу поиска с сохранёнными фильтрами, скроллит и читает список вакансий как обычный пользователь.
3. Новые (ранее не виденные) вакансии сохраняются в Data Store со статусом `new`.
4. LLM Layer оценивает релевантность каждой новой вакансии по резюме и критериям пользователя → фильтрует шум.
5. Для релевантных вакансий LLM генерирует черновик сопроводительного письма.
6. Notifier отправляет пользователю карточку: вакансия + черновик + кнопки решения.
7. При подтверждении пользователем Browser Worker (в отдельном, не пакетном запуске) открывает вакансию и отправляет отклик с текстом.
8. Статус вакансии обновляется в Data Store; при отказе — тоже фиксируется (для аналитики, что не заходит).

## 5. Почему важен "человеческий паттерн" — риски без него

Антибот-системы обычно детектируют не факт автоматизации самого по себе, а **статистические аномалии** в поведении:

- слишком равномерные интервалы между действиями (ровно каждые 60 секунд);
- нулевое время "чтения" карточки вакансии перед откликом;
- отклики 24/7 без ночных пауз;
- одинаковый порядок действий на каждой странице;
- отсутствие "лишних" действий (просмотр без отклика, возврат назад, повторные заходы на одну и ту же вакансию).

Последствия: капча, теневой бан (аккаунт работает, но отклики не долетают до работодателей), полная блокировка аккаунта.

## 6. Требования к человеческому паттерну поведения

### 6.1 Тайминг и расписание

- Отказ от жёсткого cron ("каждые 15 минут ровно"). Использовать **случайный джиттер**: базовый интервал ± 20–40%.
- Ограничение активных часов: имитация "рабочего" графика пользователя (например, 8:00–23:00 по местному времени), с редкими исключениями, а не строгим окном.
- Внутри сессии — переменное количество проверок подряд (иногда 1 заход, иногда несколько с паузами), а не одинаковый ритм день в день.

### 6.2 Действия внутри сессии

- Перед открытием карточки вакансии — эмуляция скролла списка результатов (постепенного, с остановками), а не мгновенный переход по прямой ссылке.
- Время на странице вакансии перед действием — случайное, коррелирующее с длиной текста описания (дольше на вакансии с длинным описанием), а не фиксированная задержка.
- Периодические "холостые" действия: открыть вакансию и закрыть без отклика, зайти в свой профиль, посмотреть похожие вакансии — то, что делает обычный человек, но не делает бот, нацеленный только на отклик.
- Разнообразие траектории движения курсора и скролла (не линейные, равноускоренные движения).

### 6.3 Лимиты и объём

- Дневной лимит откликов ниже официального лимита площадки, а не впритык к нему.
- Не более N вакансий с одинаковым названием компании/должности подряд без паузы — иначе паттерн "рассылка по списку" виден по самой последовательности.
- Рандомизация порядка обработки, если несколько вакансий готовы к отклику одновременно (не строго по времени публикации).

### 6.4 Технический fingerprint

- Постоянный, не пересоздаваемый браузерный профиль (те же cookies, размер окна, шрифты, часовой пояс) — смена fingerprint между запусками сама по себе подозрительна.
- Один и тот же User-Agent и параметры окружения на протяжении всей работы аккаунта.
- Запуски с одного и того же IP/сети, к которой пользователь обычно подключается (без частой смены прокси/гео).

### 6.5 Content-паттерн

- Сопроводительные письма не должны быть шаблонно похожи друг на друга по структуре — LLM должен получать инструкцию варьировать формулировки, а не просто подставлять название вакансии в один и тот же шаблон.
- Избегать откликов на вакансии, явно не соответствующие резюме (по опыту, грейду, локации) — сама LLM-фильтрация снижает "спам-сигнал" не хуже, чем поведенческая маскировка.

## 7. Human-in-the-loop как часть анти-детект стратегии

Обязательное подтверждение пользователем перед отправкой — не только этическая мера, но и техническая:

- Реальная пауза между "увидели вакансию" и "отправили отклик" (минуты/часы, а не секунды) сама по себе неотличима от поведения живого человека.
- Пользователь может передумать/отредактировать письмо — это создаёт естественную вариативность, которую сложно было бы правдоподобно сымитировать искусственно.

Рекомендуемый режим: **полностью автоматический мониторинг + полуавтоматический отклик** (черновик — на подтверждение).

## 8. Хранение данных

Минимальная схема Data Store:

| Поле | Описание |
|---|---|
| `vacancy_id` | идентификатор вакансии на hh.ru |
| `title`, `company`, `url` | базовые атрибуты |
| `first_seen_at` | когда впервые обнаружена |
| `relevance_score` | оценка LLM |
| `status` | new / notified / drafted / confirmed / sent / skipped / rejected_by_employer |
| `cover_letter_draft` | текст черновика |
| `sent_at` | момент фактической отправки |

Это нужно, чтобы: не показывать одну вакансию дважды, вести статистику конверсии, иметь возможность разобраться, если аккаунт получит ограничение (что именно могло вызвать подозрение).

## 9. Технологический стек (предварительно, без кода)

| Слой | Технология |
|---|---|
| Браузерная автоматизация | Playwright (persistent context) |
| LLM | Qwen (локально через Ollama / vLLM) |
| Очередь/оркестрация | простой планировщик с джиттером (не голый cron) |
| Хранилище | SQLite/Postgres — таблица вакансий и статусов |
| Уведомления | Telegram Bot API |

## 11. Итоговый принцип

Система должна вести себя как **внимательный, но не роботизированный пользователь**: неравномерно по времени, избирательно по содержанию, с реальными паузами на решения. Чем больше вариативности и "лишних" действий заложено в паттерн, тем ниже риск для аккаунта — и одновременно это единственный подход, совместимый с этичным использованием площадки.
