# Ключевые решения

Черновик. Перепиши каждый пункт своими словами.

1. **Браузер вместо API.** Публичный API поиска вакансий hh.ru с 2026 года закрыт для неавторизованных запросов, поэтому данные берутся через Playwright под сессией пользователя с постоянным профилем.
2. **Человек подтверждает каждый отклик.** Снижает риск блокировки аккаунта и защищает от плохих писем: LLM предлагает, человек решает.
3. **Локальная модель для оценки.** Резюме и переписка — персональные данные; локальная Qwen2.5 через Ollama не отправляет их наружу и бесплатна при сотнях вакансий в день.
4. **Постобработка ответа модели.** 7B-модель нарушает инструкции: оставляет плейсхолдеры, путает фамилию, вставляет ИИ-штампы. Детерминированные правки после генерации надёжнее, чем ещё одно правило в промпте.
5. **Контекст 8192 токена.** Резюме + вакансия + инструкции занимают около 5 тыс. токенов; при стандартном контексте Ollama часть промпта молча обрезалась бы.
6. **Межпроцессная блокировка на Ollama.** Два агента (hh и Habr) одновременно нагружали одну 7B-модель и тормозили друг друга до зависания.
7. **LLM + словарь в анализе рынка.** Модель находит навыки, которых нет в словаре; словарь страхует от пропуска очевидного. Ответы модели кэшируются, чтобы повторный отчёт не стоил новых запросов.
8. **Единый интерфейс LLM-провайдера.** Код оценки вызывает `LLMProvider.complete(messages, schema)`, а модель выбирается строкой `LLM_PROVIDER` в `.env`: Ollama, GigaChat, YandexGPT или любой OpenAI-совместимый API. Схема ответа передаётся каждой модели тем способом, который она понимает (format в Ollama, response_format, jsonSchema, инструкция в промпте у GigaChat), а проверка ответа одна для всех. Это нужно для сравнения моделей на одном наборе вакансий и для переключения на облако, если локальной видеокарты не хватает.
9. **Повторы только для временных сбоев.** Сеть, 5xx и 429 повторяются до трёх раз с растущей паузой и случайной добавкой; ошибки ключа, баланса и формата запроса — нет, повтор их не исправит. Таймаут локальной модели тоже не повторяется: вторая попытка ждала бы столько же.
10. **PostgreSQL + pgvector вместо SQLite.** Одна база хранит и вакансии, и векторы фрагментов для поиска по смыслу (RAG), и состояние агента — не нужна отдельная векторная база. SQLite остался режимом по умолчанию: без `DATABASE_URL` бот работает как раньше, переход плавный.
11. **Схемой управляют миграции Alembic.** На Postgres бот не создаёт таблицы сам, а проверяет, что миграции применены. Изменения схемы версионируются и откатываются; перенос данных сверяет число строк и набор ID в каждой таблице.
12. **Нарезка по разделам вакансии, а не по числу символов.** В текстах hh.ru разделы почти всегда начинаются строкой-заголовком с двоеточием; фрагмент про одну тему («требования») ищется точнее, чем вся вакансия или случайный кусок. К каждому фрагменту приписаны должность и компания, чтобы он был понятен сам по себе.
13. **Гибридный поиск + реранкер.** Векторы находят смысл, но размывают точные названия технологий; полнотекстовый поиск наоборот. RRF объединяет списки по местам, не сводя разные шкалы оценок. Реранкер (cross-encoder) читает вопрос и фрагмент вместе — точнее, но медленнее, поэтому только на топ-20. Замер на 40 вопросах: MRR 0.70 (векторы) → 0.75 (гибрид) → 0.86 (гибрид + реранкер).
14. **Векторы без пакета pgvector для Python.** Вектор передаётся строкой и приводится к типу vector в SQL — на одну зависимость меньше.
15. **RAG в боте считается на процессоре.** На 8 ГБ видеопамяти Ollama (7B) и модели RAG мешают друг другу до зависания; на процессоре запрос медленнее на несколько секунд, зато бот не встаёт. Переключается настройкой RAG_BOT_DEVICE.
16. **Один поток графа на вакансию.** Пауза на решение человека — это запись в базе, а не ожидающий код: бот продолжает искать вакансии, а нажатие кнопки возобновляет поток конкретной вакансии с того же места. Узел с interrupt() не делает ничего, кроме паузы — при возобновлении LangGraph выполняет его заново.
17. **Путь графа задан жёстко, свобода модели — только в тексте письма.** 7B-модель ненадёжно выбирает следующий шаг сама; маршрут (порог оценки, кнопки) определяется кодом, модель оценивает и пишет.
18. **Синхронный PostgresSaver в потоке вместо асинхронного.** Асинхронный psycopg не работает с ProactorEventLoop на Windows, а Playwright требует именно его. Асинхронные методы checkpointer'а выполняют синхронные через asyncio.to_thread — граф остаётся асинхронным, цикл событий не блокируется.
19. **Решения человека — отдельная таблица, а не только статус вакансии.** Из истории «переписать → переписать → принять» считаются метрики качества писем и согласие модели с человеком; статус хранит только итог.
